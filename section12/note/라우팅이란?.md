## 페이지 라우팅이란?

**경로에 따라 알맞은 페이지를 렌더링 하는 과정**

- ex) /new -> new 페이지 렌더링
- 사용자, 브라우저, 웹서버의 관계에서 하나의 요청-응답 사이클로 설명하면
  - 블로그 접속(사용자) -> 웹서버로 /blog 요청(브라우저) -> blog 페이지 반환(웹서버) -> 블로그 페이지 사용자 브라우저에 렌더링(브라우저)
  - 이러한 과정을 페이지 라우팅이라고함

## 페이지 라우팅의 원리

1. MPA
   - 하나의 서버가 여러개의 html 을 가지고 있다가 브라우저의 요청시 알맞은 html을 응답하는 전통적인 구조.
   - 동작방식이 직관적이고 많은 서비스가 사용하는 전통적인 방식
   - 미리완성되어 있는 페이지를 브라우저로 응답해주는 방식을 **서버사이드 랜더링** 이라고함
     - MPA랑 SSR은 다른 개념이다. MPA는 한서버 자체에 완성된 html들을 가지고 있는 구조 자체를 MPA라고 하는것이고, SSR은 완성된 페이지를 브라우저로 응답해주는 매커니즘을 이야기 하는것이기에 MPA는 html 관리 방식? 인것 같고 SSR은 브라우저 렌더링 방식 인것 같다
   - 리엑트는 MPA 방식을 따르지 않음. -> 페이지의 이동을 빠르게 처리하기 어렵기 때문이라고함. -> 왜? 도 공부해야함.
     1. 페이지 이동시 이동방식이 매끄럽지 않고 새로고침됨
     2. 새로운 페이지 렌더링시 기존페이지와 동일한 부분(ex. header, footer..)도 다시 렌더링 해줘야함. (새로운 페이지를 받아서 브라우저가 렌더링 하는것이기에 ㅇㅇ)
     3. 여러 사용자가 몰리게 되면 html을 가진 웹서버에 부하가 발생
        - 웹서버 인프라 비용, 트래픽이 불필요하게 2번 서버를 거침.(불필요한 네트워크 부하도 있을것 같다.)
2. SPA(Single Page Application)

- 리엑트는 MPA와 정반대의 방식인 SPA 방식을 채택함
- 리엑트를 사용하는 웹서버에 사용자가 접속(요청)을 하게 되면 리액트 웹서버는 index.html을 전달해줌
  - 그 어떤 경로의 요청을 했던간에 무조건 브라우저에 index.html을 전달해준다고함
  - index.html은 리액트앱 생성시에 존재하는 '리액트의 빈껍데기' 역할을 하는 파일이라고함.
    - 해당 파일은 앱의 main.jsx 파일을 실행시키는 동작만 수행함.
- 하지만 index.html만 랜더링되면 빈 화면이 노출됨
- 리액트 웹서버는 브라우저로 JS files의 묶음을 하나의 파일로 만들어 후속으로 전달해줌
  - 이렇게 JS files을 묶어서 하나의 파일로 만드는 작업을 Bundling, 묶인 파일을 Bundle file 이라고함.
  - 그리고 이런 번들링 작업은 항상 사용했던 vite가 담당한다고함
  - **우리가 만든 컴포넌트, js 파일 모두 vite가 번들링해서 번들파일로 브라우저에 전달함**
- 브라우저로 전달된 index.html 은 main.jsx를 실행한다.
  - 아래 코드는 main.jsx의 코드이고 render() 내의 <App /> 컴포를 실행해 렌더링하는 과정을 거친다.
  ```
  createRoot(document.getElementById('root')).render(
    <App />
  )
  ```
- **이렇게 컴포넌트들이 화면에 렌더링 되고 이렇게 브라우저가 직접 렌더링하는 방식을 CSR(Client Side Rendering)**
- 그리고 이런 번들파일을 사실상 리액트 앱이라고 할수 있다고함

- 그럼 어떻게 MPA 동작방식과 다를까?
  - SPA와 리액트는 사용자가 새로운 화면으로 이동해도 웹서버에 새로운 요청을 하지 않음
  - 처음 전달받은 index.html과 리액트앱(번들파일)로 새로운 페이지를 브라우저에서 직접 렌더링한다고한다.
    - 어짜피 index.html은 빈캔버스임. 요청에 따라 서로 다른 컴포넌트들 랜더링하는 방식인듯
    - 근데 그럼.. css파일은? 이렇도 다 리액트앱 내에 있어서 그런가?
